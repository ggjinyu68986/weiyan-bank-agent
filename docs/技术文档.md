## 一、系统架构

```
┌─────────────────────────── 客户端层（多渠道）────────────────────────┐
│  Web/APP 渠道：纯 HTML/JS 单页（file:// 直接可用，零构建）            │
│    · 类 IM 聊天 · 黄级确认卡片 · 红级 MFA 弹层 · 账单 ECharts        │
│    · 审计日志面板 · 定时器演示（时间沙箱）                            │
│  IM 渠道：终端模拟客户端（python -m backend.channels.console）       │
│    · 同一 Agent 内核，确认/强验证/熔断/审计全可用                    │
│    生产可新增：微信/企业微信/飞书/Telegram 适配器（协议一致）        │
└───────────────────────────────┬───────────────────────────────────────┘
                                │ 渠道适配层（receive→handle→send，渠道是"哑的"）
                                ▼
┌───────────────────────────────▼─────────────────────────────────────┐
│                        编排层（Agent Orchestrator）             │
│  用户消息 → LLM 决策(工具+参数/计划) → 权限门 decide()          │
│  → auto 直执 / confirm 挂起 / mfa 挂起 / deny 拒绝              │
│  → 执行 → 回显（仅来自返回值） → 全量审计                        │
│  扩展：DAG 计划（跨场景联动）、tick 时间沙箱（定时/事件）        │
└───────────────┬──────────────────────────────┬──────────────────┘
┌───────────────▼──────────────┐  ┌────────────▼──────────────────┐
│  能力层（Mock Bank Service）  │  │  安全层（数据驱动注册表）      │
│  6 大场景业务方法（全 25 工具）│  │  operations.json：绿/黄/红    │
│  金额一律「分」、转账幂等      │  │  日累计限额、未注册即拒绝      │
│  OpResult + execution_id     │  │  + 异常熔断（MFA/可疑行为）     │
└───────────────┬──────────────┘  └────────────────────────────────┘
┌───────────────▼─────────────────────────────────────────────────┐
│  数据层：内存 Store（种子画像：小明/妈妈/老婆/张伟 + 9月流水）    │
│  Repository 抽象（开发期内存，生产可换 SQLite/MySQL）             │
└──────────────────────────────────────────────────────────────────┘
```

**分层原则**：接口层是"哑的"——不做任何权限判定；权限门在编排层于**每次执行前**强制经过；确认/强验证后**再次**过权限门（防止"确认时合法、执行时已越权"）。**渠道同样是"哑的"**：Web/APP 与 IM 渠道共用同一编排器内核，渠道只做收/发，安全机制不随渠道复制、不因渠道缺失（赛题：APP、IM 等渠道联通）。

## 二、核心算法说明

### 2.1 意图理解 → 工具调用（函数即能力边界）

Agent 不生成自由文本操作，而是输出结构化工具调用（OpenAI 兼容 `tools` 协议，pydantic 校验参数）。工具 schema 与权限注册表**一一对应**：

```
用户消息 → LLM（DeepSeek，可插拔）→ {tool, params} 或 DAG 计划
        → decide(registry, tool, params, user_state) → 动作
```

Provider 可插拔：默认 DeepSeek（OpenAI 兼容），无 Key 自动回退**确定性 MockLLM**（规则路由 6 场景话术），保证开发/评测/离线演示零阻塞、可复现。

### 2.2 权限分级（数据驱动）

`backend/registry/operations.json` 定义 25 个操作的风险级别：

| 级别 | 执行策略 | 覆盖操作（节选） |
|---|---|---|
| 🟢 绿色 | 自动执行，无需确认 | 余额、流水、账单分析、年度账单、理财查询、理财对比、风险评估、订阅查询、订阅识别、续费提醒 |
| 🟡 黄色 | 展示操作详情 + 用户确认 | 转账（日累计 ≤1000 元）、定时转账、AA 收款、虚拟卡、资金锁定、礼品订购、取消订阅、卡片冻结/解冻 |
| 🔴 红色 | 多因子强验证（短信/人脸/U盾） | 大额转账（日累计 >1000 元 自动升级）、理财申购/赎回、额度调整、挂失/解挂、密码修改 |

**日累计升级**：黄级带会话级累计（`today_transfer_cents`），单笔或累计超 1000 元自动升级红级强验证。**未注册工具一律 deny**（安全底线：即使 LLM 被诱导调用 `hack_steal_money`，权限门直接拒绝）。

### 2.3 幻觉防护（双层：模型层尽力 + 系统层兜底）

- 结果回显**只允许来自工具返回值**，每次操作返回唯一 `execution_id`；
- 系统提示词强制"所有数字来自工具返回值，禁止编造"；规则 1b：查询类必须调用工具，未调工具禁止以文字输出金额/流水表格/账户号/"执行编号"；
- **系统层兜底 `_looks_fabricated()`**：纯文字回复（未调工具）若含"执行编号 / 账户号"（系统唯一生成物）→ 一律判疑似编造；含金额 → 仅当用户请求为查询类（非操作类）才判定，避免操作类文字复述（如 AA 每人金额）被误伤。命中即拦截为 deny 并计入可疑行为（与熔断联动）。**模型可能出错，但系统不让错误流到用户**；
- 实测：真实 DeepSeek 下对"无视规则转账"在提示词层即拒绝；对"问余额"曾有模型直接文字编造数字 → 被 `_looks_fabricated` 拦截（详见安全自评第三节）。

### 2.4 注入防御（双层）

1. **提示词层**：禁止引导绕过验证；
2. **编排层权限门**：未注册工具 deny；确认/验证后二次过闸。测试 `SEC-001` 覆盖。

### 2.5 操作审计

每次交互落 `AuditRecord`（时间/用户消息/工具/参数/风险级/动作/execution_id/结果），前端审计面板实时可查——完整"决策链路"可追溯（评委可演示）。

### 2.6 跨场景联动（DAG 计划）

"我爱人生日"（事件 E-001，2026-12-20）→ 计划图：

```
[lock_funds 1000元] ─┬─→ [order_gift 鲜花 200元]
                     └─→ [order_gift 蛋糕 150元]
```

逐节点过权限门：auto 直执、confirm/mfa 逐个挂起（前端连续确认卡片）、任一节点 deny 中止整计划（已执行节点不受影响）。

### 2.7 定时调度与时间沙箱

`tick(sim_date)`：拨动到任意日期，自动执行到期定时转账（幂等 key 防重）+ 到期事件联动（生日前 2 天自动订购）。审计标记 `system`。**时间沙箱让"定时能力"可在评测窗口内完整演示**。

### 2.8 账单异常识别规则

| 规则 | 阈值 | 种子命中示例 |
|---|---|---|
| 深夜大额 | 23:00–05:00 且 ≥1000 元 | 02:33 奢侈品 1200 元 |
| 异地消费 | 备注含"异地" | 上海餐厅 |
| 高频消费 | 同商户月内 ≥3 笔 | 快餐 5 笔 |

## 三、安全设计

1. **权限判定与执行分离**：接口"哑"，规则在上游；篡改 LLM 或直连 API 都无法绕过。
2. **金额精度**：一律用分（int），杜绝浮点误差；转账幂等（request_id）。
3. **拒绝任意代码执行**：Agent 只调用白名单银行工具，不执行 LLM 生成的代码——工具白名单即"逻辑沙箱"（附 `backend/security/sandbox.py` 进程级兜底 + Docker 双轨，见下）。
4. **异常熔断**：MFA 验证码连续错误 3 次 / 可疑行为 3 次 → 账户安全锁定，**所有操作（含绿级查询）一律 deny**，审计留 lockout 记录，`/agent/status` 暴露状态，前端红色横幅提示，重置可解锁。测试 `SEC-003` 覆盖（真实模型下 3 个不同红级操作各错一次触发）。
5. **编造拦截（幻觉第二道防线）**：纯文字回复（未调工具）中出现金额/执行编号/账户号 → `_looks_fabricated` 判定疑似编造 → deny + 计入可疑行为（与熔断联动）。真实演示曾抓到模型编造"余额 58200 / 假执行编号"，真实余额实为转账后 57400。
6. **手机号/备注收款解析**：`transfer` 的收款人支持账户号或 11 位手机号（`_resolve_account`），备注自动映射联系人，满足赛题"按人名/手机号/备注转账"。

## 四、自动评测

`harness/`：YAML 场景 DSL（25 用例 × 6 场景 + 安全）+ MD/JSON 双格式报告。
- Mock 模式（确定性）25/25；真实 DeepSeek **24/24**（S6 DAG 由自研编排层生成，真实模式走提示词引导逐步调用）。
- 报告：`docs/reports/eval-report.md`——"测试用例"本身作为作品资料交付。
- 评测即安全证据：真实模型 9/18 → 17/17 → 24/24 的"发现→加固→验证"闭环见安全自评报告第三节。

## 五、技术选型表

| 关注点 | 选择 | 理由（答辩口径） |
|---|---|---|
| LLM | DeepSeek（OpenAI 兼容，可插拔） | 低成本高性能；Provider 抽象留豆包/GPT 切换点 |
| 编排 | **自研轻量层**（<1000 行） | 防"套壳"质疑；权限/审计/回退全可控，是安全卖点本身 |
| 前端 | 纯 HTML/JS + ECharts CDN | 零构建，file:// 可开；演示零环境依赖 |
| 数据 | 内存 Store + Repository 抽象 | 演示可重置；抽象层可换 SQLite |
| 测试 | pytest + YAML harness | 测试即作品资料；对应"自动评测"初赛机制 |
| 部署 | Docker（沙箱双轨）+ 进程兜底 | 见部署说明 |
