## 一、系统架构

```
┌─────────────────────────── 客户端层（全渠道 H5 形态）──────────────────────┐
│  手机银行风格单页（file:// 直接可用，零构建、零依赖）                        │
│    7 Tab：对话 / 账单 / 理财 / 卡片 / 联系人 / 订阅 / 审计                    │
│    资产卡 · 黄级确认卡 · 红级 MFA 弹层 · 问卷点选卡 · 人工接管流程卡          │
│    账单环形图（ECharts）· AA 收款进度卡 · 订阅续费提醒条                     │
│  （答辩口径：同一内核可接 APP / IM / 语音渠道，渠道是"哑的"，安全不随渠道复制） │
└───────────────────────────────┬───────────────────────────────────────┘
                                │ 渠道适配层（receive → handle → send）
                                ▼
┌───────────────────────────────▼─────────────────────────────────────┐
│                    编排层（Agent Orchestrator，自研 <1200 行）        │
│  用户消息 → LLM 决策（工具+参数）→ 权限门 decide()                     │
│    → 绿 auto 直执 / 黄 confirm 挂起 / 红 mfa 挂起 / deny 拒绝          │
│    → 执行 → 回显（仅来自工具返回值）→ 全量审计                        │
│  确定性路由：生日 DAG 计划 · 卡片 card-op · 订阅 subscription-op       │
│  时间沙箱 tick（定时任务 + 生日事件引擎）· 人工接管 handoff 闭环        │
└───────────────┬──────────────────────────────┬──────────────────┘
┌───────────────▼──────────────┐  ┌────────────▼──────────────────┐
│  能力层（Mock Bank Service）  │  │  安全层（数据驱动注册表）      │
│  6 大场景业务方法（全 34 工具）│  │  operations.json：绿18/黄10/红6 │
│  金额一律「分」、转账幂等      │  │  日累计限额升级 · 未注册即拒绝  │
│  OpResult + execution_id     │  │  异常熔断（MFA/可疑行为 3 次锁定）│
│  决策层：确定性规则 ⊕ JEV      │  │  人工接管工单 · 审计全链路       │
└───────────────┬──────────────┘  └────────────────────────────────┘
┌───────────────▼─────────────────────────────────────────────────┐
│  数据层：内存 Store（种子画像 6 用户 + 全年 12 个月流水画像）       │
│  Repository 抽象（开发期内存，生产可换 SQLite/MySQL）             │
└──────────────────────────────────────────────────────────────────┘
```

**分层原则**：
1. **接口层"哑"**——不做任何权限判定；权限门在编排层于**每次执行前**强制经过；
2. **确认后二次过闸**——确认/强验证后**再次**过权限门（防止"确认时合法、执行时已越权"的状态变化）；
3. **渠道"哑"**——Web/IM/语音共用同一编排器内核，安全机制不随渠道复制、不因渠道缺失（赛题：APP、IM 等渠道联通）；
4. **高价值操作确定性路由**——生日联动、卡片操作、订阅操作不走模型自由发挥，由编排层确定性构造并逐节点过权限门（防幻觉、防注入的工程化手段）。

## 二、核心算法说明

### 2.1 意图理解 → 工具调用（函数即能力边界）

Agent 不生成自由文本操作，而是输出结构化工具调用（OpenAI 兼容 `tools` 协议，pydantic 校验参数）。工具 schema 与权限注册表**一一对应**：

```
用户消息 → LLM（DeepSeek，可插拔）→ {tool, params}
        → decide(registry, tool, params, user_state) → 动作
```

Provider 可插拔：默认 DeepSeek（OpenAI 兼容），无 Key 自动回退**确定性 MockLLM**（规则路由 6 场景话术），保证开发/评测/离线演示零阻塞、可复现。

### 2.2 权限分级（数据驱动注册表）

`backend/registry/operations.json` 定义 **34 个操作**（绿 18 / 黄 10 / 红 6）：

| 级别 | 执行策略 | 覆盖操作 |
|---|---|---|
| 🟢 绿色（18） | 自动执行，确认意图后直接执行，无需二次确认 | 余额查询、交易记录、账单分析、年度账单、理财收益/在售/对比/推荐、风险评估、订阅查询/识别/续费提醒、AA 进度、联系人列表 |
| 🟡 黄色（10） | 执行前展示操作详情 + 用户明确确认 | 转账（日累计 ≤1000 元）、定时转账、AA 收款、虚拟卡申请、资金锁定、礼品订购、取消订阅、卡片冻结/解冻 |
| 🔴 红色（6） | 多因子强验证（短信验证码/人脸/U盾） | 大额转账（日累计 >1000 元自动升级）、理财申购/赎回、额度调整、挂失/解挂、密码修改 |

**日累计升级**：黄级带会话级累计（`today_transfer_cents`），单笔或累计超 1000 元自动升级红级强验证。**未注册工具一律 deny**（安全底线：即使 LLM 被诱导调用未注册工具，权限门直接拒绝）。

### 2.3 幻觉防护（双层：模型层尽力 + 系统层兜底）

- 结果回显**只允许来自工具返回值**，每次操作返回唯一 `execution_id`；
- 系统提示词强制"所有数字来自工具返回值，禁止编造"；查询类必须调用工具，未调工具禁止以文字输出金额/流水表格/账户号/"执行编号"；
- **系统层兜底 `_looks_fabricated()`**：纯文字回复（未调工具）若含"执行编号 / 账户号"（系统唯一生成物）→ 一律判疑似编造；含金额 → 仅当用户请求为查询类（非操作类）才判定，避免操作类文字复述被误伤。命中即拦截为 deny 并计入可疑行为（与熔断联动）；
- **双引擎**：确定性规则 ⊕ JEV 决策模型（见 2.11），任一判"疑似编造"即拦截；
- 实测：真实 DeepSeek 下曾出现模型直接文字编造"余额 58200 / 假执行编号" → 被 `_looks_fabricated` 拦截（详见安全自评报告）。

### 2.4 注入防御（双层）

1. **提示词层**：禁止引导绕过验证；
2. **编排层权限门（核心）**：未注册工具 deny；确认/验证后二次过闸；连续注入/越权试探 3 次触发熔断锁定。**权限控制不依赖模型自觉**——即使 LLM 被注入成功，工具白名单 + 权限门仍拦截。

### 2.5 操作审计

每次交互落 `AuditRecord`（时间/用户消息/工具/参数/风险级/动作/execution_id/结果/决策引擎判定），前端「审计」Tab 实时可查——完整"决策链路"可追溯（评委可直接演示）。

### 2.6 跨场景联动（确定性生日 DAG + 事件引擎）

"我爱人生日，当月锁定 1000 元，生日前 2 天订购鲜花蛋糕" → 编排层**确定性构造 3 节点 DAG**（不走模型自由发挥）：

```
[n1 lock_funds 1000元] ─┬─→ [n2 order_gift 鲜花 200元]
                        └─→ [n3 order_gift 蛋糕 150元]   ← n2/n3 depends n1
```

- **逐节点过权限门**：每节点黄色确认（前端连续确认卡），任一节点拒绝即中止整计划（已执行节点保留、未执行节点无副作用）；
- **金额确定性**：锁定金额优先解析用户指定（如"锁定1000元"），未指定默认 1000/200/150 元；模型不参与算钱；
- **事件引擎**：`tick` 拨动到生日前 2 天自动订购鲜花+蛋糕，**幂等**（不重复下单）；
- 真机验证：3 节点全部确认完成 → 余额 58200 − 1000（锁定）− 200（鲜花）− 150（蛋糕）= 56850 ✓；tick 2026-12-18 → 事件触发 1 个。

### 2.7 定时调度与时间沙箱

`tick(sim_date)`：拨动到任意日期，自动执行到期定时转账（幂等 key 防重）+ 到期事件联动。审计标记 `system`。**时间沙箱让"定时能力"可在评测窗口内完整演示**（含"每周给妈妈转500元"→ 到期自动扣款）。

### 2.7.1 确定性时间解析（模型出意图，系统出事实）

**问题**：定时转账的 `next_run` 日期若由 LLM 计算，属于幻觉高发区（跨月/跨年/周几换算极易错），银行对时间精确性有硬性要求，且评测/演示需要可复现。

**方案**（`backend/agent/timeexpr.py`）：

```
用户说「明天给老婆转100元」
  → LLM 只输出意图：schedule_transfer(next_run_expr="明天", cycle_days=0)  ← 不填死日期
  → 系统确定性解析：resolve("明天", base=今天) = 2026-09-28                ← 可单测、可审计
  → 登记 next_run=2026-09-28，拨动该日期触发扣款
```

| 表达式 | 解析结果（base=2026-09-27） |
|---|---|
| `明天` / `后天` | base+1 / base+2 |
| `N天后` / `N天前` | base+N / base-N |
| `下周X` | 下一个周一所在周的星期 X |
| `下个月X日` | 下月 X 日 |
| `一分钟后` / `马上`（分钟级≈尽快） | 当天 base |
| `每周` / `每月`（周期词） | 不产生日期 → 固定锚点 2026-10-05（演示可复现） |
| `YYYY-MM-DD` | 用户明确日期，直接使用 |

- **优先级**：用户明确日期 `next_run` > 相对表达式 `next_run_expr`（系统换算）> 默认锚点。
- **提示词硬约束**：`严禁自己推算日期`——模型只填表达式，由系统换算。
- **答辩口径**：时间计算是幻觉高发区，模型只负责把"明天/每周"翻译成结构化意图，日期换算由确定性时间服务完成——每笔定时任务的时间**可计算、可审计、可复现**（`tests/test_timeexpr.py` 8 项，固定基准断言不随真实日期漂移）。

### 2.8 账单异常识别规则

| 规则 | 阈值 | 种子命中示例 |
|---|---|---|
| 深夜大额 | 23:00–05:00 且 ≥1000 元 | 深夜消费 3200 元 |
| 异地消费 | 备注含"异地" | 上海某餐厅 |
| 高频消费 | 同商户月内 ≥3 笔 | 某某快餐 5 笔 |

**年度账单**：seed 补充全年 12 个月收支画像 → `annual_report` 输出月度收支趋势 + 年度汇总（前端「账单」Tab 月度/年度切换）。

### 2.9 联系人簿（按人名转账的解析依据）

赛题"按人名转账"依赖"人称 → 收款账户"的**可解释解析**：

```
用户说「给妈妈转800元」
  → 联系人簿（name/aliases/phone → account_id）解析
  → 确认卡展示「收款人：妈妈（账户 6222-1001）」待用户确认   ← 防转错人
  → 确认后执行 + 全量审计
```

- **数据模型** `Contact`：name + aliases（别名）+ phone + account_id + relation。种子预置 5 位联系人；
- **解析顺序**（`_resolve_account`）：账户号直查 → 联系人簿（姓名/别名/手机号）→ 11 位手机号查用户表；
- **安全语义**：同名/查不到 → Agent 主动询问澄清，**绝不猜测**；确认卡始终展示收款人全名 + 账户号，防止"AI 把钱转错人"（转账诈骗的典型防线）；
- **前端**：「联系人」Tab——列表 + 添加表单；转账确认卡反查联系人簿显示收款人姓名。

### 2.10 AA 拆分收款（完整资金闭环）

```
用户说「聚餐600元3个人AA」
  ① split_bill（黄级确认）：人均=整除、余数归发起人；向其余 N-1 人各收人均金额
  ② split_bill_status（绿级）：已收 X/N、已付/待付名单（前端进度卡）
  ③ pay_split_bill（黄级确认）：收款人确认付款 → 扣款 → 入账发起人
     → 重复付款拒绝（幂等）→ 全部付清自动 settled
```

- **确定性计算**：人均金额系统整除得出（模型不参与算钱），金额一律分，余数归发起人，总数分毫不差；
- **对端前端**：AA 收款进度以可视化进度条卡片展示（收款人/金额/已收/待收），支持「XX 已付款」语音/文字入账；
- **参数宽容（真机加固）**：收款人支持账户号 / 联系人姓名 / 手机号，统一走 `_resolve_account` 解析。

### 2.11 双引擎决策层（确定性规则 ⊕ JEV 决策模型）

**背景**：权限分级、幻觉校验、工具路由是系统的三个核心判定点。基线用确定性规则（可审计、可复现、注入不可绕过），引入 **JEV**（TypeSafe AI System One 决策模型：不生成文本，输入状态 + 类型化问题 → 返回结构化判定 + 概率 + 置信度）作为**并行决策引擎**，让每个安全判定带可解释的置信度。

**三个判定点**（`backend/agent/decision.py`）：

| 判定点 | 规则引擎（基线） | JEV 增强 | 合并策略 |
|---|---|---|---|
| 权限分级 | 注册表 + 日限额 | 判 绿/黄/红 + 置信度 | **保守合并**：JEV 只能更严格（live 且置信 ≥0.85 才升级），绝不降级/放行 |
| 幻觉校验 | 执行编号/账户号铁证 | 判"是否疑似编造" | 任一判真即拦截（规则是硬底线） |
| 工具路由 | —— | 用户意图与所选工具是否匹配 | **记录型**：只写入审计，不阻断 |

**三态可插拔**（环境变量 `JEV_MODE`）：`off` 纯规则（评测/离线基线）；`mock` 确定性伪 JEV（镜像规则结果 + 合理置信度，离线可演示、可复现）；`live` 真实 JEV API（无 Key / 断网 / 超时**自动回退 mock**，绝不阻塞业务）。

**答辩叙事**：判定与执行分离（JEV 只产出判定，执行仍走权限门链路）；规则是底线（JEV 负责"更严格地怀疑"，不负责"放行"）；判定过程可视化（确认卡/强验证弹层/审计面板显示「规则黄 ⊕ JEV 黄 · 置信 93%」）。

### 2.12 风险测评问卷（对话式状态机，不依赖 LLM）

- 6 题 KYC 问卷（投资经验/风险偏好/亏损承受/投资期限/金融知识/损失反应），6–24 分 → 四级风险画像（保守/稳健/平衡/进取）落库 `risk_profiles` → 联动理财推荐；
- **手写状态机** `st["risk_quiz"]`（非 LLM 决策）：打字回复选项文字 或 前端点选按钮 双通道；支持取消/重问；
- 完成后自动给出「风险适配建议 + 理财配置」，含"理财非存款、产品有风险"合规提示。

### 2.13 高价值操作确定性路由（卡片 / 订阅 / 人工接管）

**问题**：真实 LLM 对"按钮触发的确定性操作"（卡片冻结/订阅取消等）响应不稳定（曾出现循环确认、误路由）。

**方案**：前端按钮**不走 LLM**，直连确定性端点：
- `POST /agent/card-op {action, card_id, amount_cents}`：apply（黄）/ freeze / unfreeze（黄）/ lock / unlock / limit（红 MFA）；
- `POST /agent/subscription-op {action: cancel|detect}`：cancel（黄确认）/ detect（绿自动）；
- **统一语义**：按钮 → 权限门 → 确认/MFA → 执行，审计与对话同源——"零模型依赖"，权限控制与业务执行完全确定。

### 2.14 人工接管闭环（赛题"中断、回退和人工接管"）

```
MFA 连续错 3 次 / 可疑行为 3 次 → 账户安全锁定
  → 一切操作 deny（含查询），前端渲染红色锁定卡「🔒 账户已安全锁定」
  → 点「📞 转人工客服」→ POST /agent/handoff → 生成服务工单 T-xxxx（重复申请返回同一工单）
  → 工单卡展示工单号 → 点「✅ 客服核实完成，解锁账户」→ POST /agent/handoff/resolve
  → 客服核实身份 → 解锁 + 熔断计数清零（mfa_failures/suspicious_count 归零）→ 恢复正常
  → 全流程审计留痕（handoff / handoff_resolve 两个动作）
```

真机验证：MFA 错 3 次 → 锁定 → deny+lockout 卡 → 工单 T-0006 → 解锁清零 → 余额查询恢复 ✓

## 三、安全设计

1. **权限判定与执行分离**：接口"哑"，规则在上游；篡改 LLM 或直连 API 都无法绕过；
2. **金额精度**：一律用分（int），杜绝浮点误差；转账幂等（request_id）；
3. **零代码执行面（逻辑沙箱）**：Agent 只调用 34 个白名单银行工具，**不执行 LLM 生成的任何代码**——工具白名单 + 权限门即"受限、可监控的逻辑隔离环境"（赛题沙箱要求的等价实现），无任意代码执行风险面；
4. **异常熔断**：MFA 连续错 3 次 / 可疑行为 3 次 → 锁定，**所有操作（含绿级查询）一律 deny**，`/agent/status` 暴露状态，前端红色横幅 + 人工接管流程卡（2.14）；
5. **编造拦截（幻觉第二道防线）**：纯文字回复（未调工具）中出现金额/执行编号/账户号 → 判疑似编造 → deny + 计入可疑行为。真实演示曾抓到模型编造余额（实际已转账扣款）；
6. **注入防御（权限门强制）**：执行前必经权限门 + 未注册工具 deny + 确认后二次过闸 + 试探累计熔断；**权限控制不依赖模型自觉**；
7. **联系人簿收款解析**：`_resolve_account` 按序解析（账户号 → 联系人姓名/别名 → 手机号），确认卡展示收款人全名 + 账户号，同名/查不到主动澄清（防转错人）；
8. **数据一致性（真机 bug 修复）**：API 层 Agent 与查询接口**共用同一 BankService 实例**——曾因独立 store 各自持有数据，表现为"转账成功但余额不变"（易被误判为模型幻觉）。已统一实例 + 回归测试 `test_api_agent_shares_service_instance`；
9. **人工接管闭环**：锁定 → 工单 → 客服核实解锁（2.14），熔断有"人"的出口，非死锁。
